# Claims registry

Every public commercial claim, mapped to the code that enforces it. The rule
(from `src/assurance/billing/plans.py`): **if it is not gated in code, it is not
on the pricing page.** A row marked `NOT ENFORCED — removed` is a claim this
site used to make and no longer does.

Verified by reading `src/assurance/billing/plans.py` and
`src/assurance/api/deps.py` (plus the route modules named below), as they exist
after the backend change that removes `cases_per_day` and `product_families`.
Public wording lives in `app/lib/plans.ts` (copied from `plans.py`), the
homepage, `README.md`, `docs/index.md`, `docs/pricing.md` and `public/llms.txt`.

The seal hashes numbers as `round(float(v), 6)`, so an integer beyond 2^53 or a fraction finer than 6 decimals is reported as a number the seal cannot distinguish (and `Evidence.seal` refuses new ones); the claim "carries no field outside the seal" holds within that limit. Machine bundles are also held to the engine's own rules (no `certified` from a trace, tier within the provenance and envelope ceilings, known provenance, non-empty checks) and always carry "a seal is not a signature". Cost control for an anonymous caller on a one-worker deployment: answers are capped (50 listed items per list, clipped strings), files over 50,000 entries are refused by size, at most 2 files are analysed at once (the rest get `503 verifier_busy`, which costs no allowance), `Content-Type: application/json` is required (415 otherwise, no allowance spent; a chunked body that then exceeds the cap has already spent its unit). ## Operational gaps — documented, not closed

These are things a reader might assume the service does. It does not; each is the operator's.

* **Reconciliation is manual.** `python -m assurance.billing.reconcile` runs when someone runs
  it. There is no scheduler in this repository, so a `past_due` account has **no automatic
  expiry** unless the operator runs it (with `--apply`) on a schedule: Stripe's own dunning
  normally ends the subscription and says so by webhook, and a lost webhook is exactly what
  reconciliation exists for. See `deploy/assurance/README.md` (Reconciliation).
* **Signing-key rotation is operator-acknowledged, per account.** After the service's
  attestation key changes, every tenant `POST /v1/ledger/attest` answers 409 until the
  operator has run `assurance attest sign --rotating` once against each account's log.
  `GET /v1/ledger/attest/key` serves only the current key and `POST /v1/ledger/attest/verify`
  without an explicit `public_key_pem` checks against it, so **attestations signed under an
  earlier key read as forged unless the verifier supplies that earlier public key**. Nothing in
  the service keeps a key history: the operator must. A lost signing key cannot be recovered
  (see the runbook in `deploy/assurance/README.md`). Pinned by the review reproducer, not by a
  test of a fix.
* **No authentication-failure rate limit.** An unknown API key is now answered from a read
  (it no longer queues for the accounts write lock), but a flood of invalid keys still costs a
  hash and a lookup each, in the request thread, and there is no per-address failure counter.
  A limiter that cannot lock out a legitimate user behind a shared address was not small
  enough to add here. Put a rate limit in front (Fly, a WAF).
* **Blocking SQLite on the event loop.** `current_principal` calls the account store
  synchronously from an `async def`; under load one slow query stalls other requests.
* **Anonymous `POST /v1/checkout`** has no per-address limit in code.
* **uvicorn trusts `X-Forwarded-For` from loopback by default** (`--proxy-headers` is on and
  `--forwarded-allow-ips` defaults to loopback, `127.0.0.1,::1`, or `$FORWARDED_ALLOW_IPS`). The quota is keyed on the socket peer, or on
  `Fly-Client-IP` when `ASSURANCE_TRUST_FLY_PROXY=1` (and only if it parses as an address).
  Behind Fly the peer is never loopback, so forwarded headers are not honoured; on a host where a
  local proxy on the same machine forwards traffic they would be.
