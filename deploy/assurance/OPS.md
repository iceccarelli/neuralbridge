# Operating the assurance service: install, cycle, upgrade, backup, restore drill, health

Status: **prepared, not performed.** Nothing in this file has been run against a production host,
and no timer, container or unit described here is installed by this repository. The commands
exist in this repository and are exercised by `tests/test_ops_cycle.py` on throwaway data. The
actions (installing, enabling, upgrading, restoring) are the operator's (`CLAUDE.md`,
"Authority"). Facts only: this page makes no claim about customers, markets or regulatory
outcomes.

`PIPELINE.md` fixes the order of the public-source pipeline and says who acts at each step. This
page covers what *runs unattended* and how to keep it healthy. The pieces:

| piece | what it is | file |
|---|---|---|
| `python -m assurance ops cycle` | one cycle of the non-human steps, recorded as one JSON line | `src/assurance/ops/` |
| `python -m assurance ops status` | last cycle, its age, the human actions it left | same |
| `python -m assurance ops check` | preflight of the config and the host | same |
| `python -m assurance ops notify-test` | dry-run or `--live` TEST webhook to a `notify` target | same |
| examples | config, cron, systemd service + timer, compose | `deploy/assurance/ops/` |

## 1. Reproducible install

What the repository pins, stated plainly:

- **Python dependencies are locked with hashes** in `requirements/*.lock`, generated by
  `scripts/lock.sh` (uv, default PyPI index only) from the `.txt` lower bounds:
  `assurance-service.lock` (the five packages of the assurance service, Python 3.12),
  `prod.lock` (the NeuralBridge platform image, Python 3.11) and `test.lock` (CI-equivalent
  test environment, universal for >=3.11). The `.txt` files and `pyproject.toml` still carry
  `>=` bounds; the lock is what gets installed.
- **Not yet using the lock:** `deploy/assurance/Dockerfile` still installs with `>=` (its test,
  `tests/test_assurance_dockerfile_deps.py`, parses that line), and CI's `test` and `lint` jobs
  still install the `.txt` files. The root `Dockerfile` installs `prod.lock`; that change was not
  built (no Docker daemon was available). `deploy/assurance/RELEASE.md` states what is and is
  not established.
- The **website** is locked (`package-lock.json`; use `npm ci`). That does not cover the service.

Install the service from the lock:

```bash
# check out the exact commit or tag you reviewed and write its full SHA in your log
python3.12 -m venv /opt/assurance/venv                       # the lock targets Python 3.12
/opt/assurance/venv/bin/pip install --require-hashes --no-deps -r requirements/assurance-service.lock
/opt/assurance/venv/bin/pip install --no-deps -e .           # the package itself, nothing resolved
/opt/assurance/venv/bin/python -m assurance capabilities --check   # exit 0: catalogue matches code
sha256sum requirements/assurance-service.lock                # record with the commit SHA
```

pip refuses the install if any downloaded file's hash is not in the lock. Record the commit SHA,
the lock's SHA-256 and `python --version`. For the container, record the image digest
(`docker image inspect --format '{{.Id}}' assurance:local`) after the build; the digest, not the
tag, is what you can redeploy.

Changing a dependency: edit the `.txt` (and `pyproject.toml` if it is a runtime dependency), run
`scripts/lock.sh` (keeps current pins; `--upgrade` re-resolves everything), commit both.
`tests/test_requirements_lock.py` fails if the lock is hand-edited, unhashed, or older than its
input. Known advisories in the locked set are listed in `deploy/assurance/RELEASE.md`.

Then, before the first cycle:

```bash
python -m assurance ops check --config /etc/assurance/ops.json
```

`ops check` validates the config and the host and lists what it does **not** check. Fix every
`[fail]` line; read the `NOT checked` list: that is the operator's remaining work.

## 2. The cycle

`ops cycle` runs, in this fixed order, calling the existing verbs in-process (it re-implements
none of them):

| # | step name | runs | skipped when |
|---|---|---|---|
| 1 | `intel.refresh:<source>` | `intel refresh --source S --store F --live [--cve …]` | config `live` is not `true`, **or** `--live` was not passed, **or** no sources configured. Recorded as `skipped`, detail `not refreshed: …` |
| 2 | `watch.run:<config>` | `watch run CONFIG --ledger L --json`, one per configured watch | none configured |
| 3 | `ledger.verify` | read-only chain walk of every `tenants/acc_<16 hex>.db` and `art14-register.db` under `data_dir` | no ledger exists |
| 4 | `attest.anchor_all` | `attest anchor-all --data-dir D --key K --max-age H --json` | no `attest.key` configured; **or ledger.verify failed** (an anchor over a known-broken chain would vouch for it) |
| 5 | `backup` | `restore_check backup DATA BACKUP_DIR/<UTC timestamp>` into a **new** directory | never skipped |
| 6 | `backup.verify` | `restore_check verify` on that directory immediately | no backup was taken |

Each step is isolated: an exception or a non-zero exit is recorded and the rest still run, except
the dependency in row 4. Nothing in the cycle opens a case, establishes awareness, decides an
Article 14 track or closes anything; those are a named person's acts (`PIPELINE.md`, "The human
acts"). The cycle only reports that a person has something to read.

### Network

The only networked step is the intel refresh, and it needs **both** `"live": true` in the config
**and** `--live` on the command line. Without either, nothing opens a socket and the step says
`not refreshed`. A watch with `max_age_hours` then reports the store stale (exit 2): that is the
intended alarm, not a bug.

### Step status and exit code

| step status | meaning |
|---|---|
| `ok` | the verb's own exit code was 0 |
| `flagged` | something for a person to read; **not a failure** (watch exit 1; intel input rejected; anchor-all refused a ledger; a backup of an already-failing source) |
| `degraded` | the verb said it could not rely on its inputs (watch exit 2, including a stale store) |
| `failed` | the verb could not run, or raised (recorded exit 70), or the chain/backup verification failed |
| `skipped` | did not run; `detail` says why |

`ops cycle` exit code mirrors `watch run`:

| exit | cycle status | meaning |
|---|---|---|
| `0` | `ok` | every step ok or skipped |
| `1` | `flagged` | nothing failed; at least one step has something for a person |
| `2` | `degraded` | any step degraded or failed; **also** the cycle could not start (bad config; `cycle already running`), in which case nothing was written |

Findings are deliberately not a failure: a systemd unit uses `SuccessExitStatus=1` so only exit 2
fails the unit. Exit 2 is shared by "degraded" and "could not start"; the record (written only
when a cycle ran) tells them apart, and `cycle already running` is on stderr.

### The cycle record

One JSON object per line, **appended** to `record` (never rewritten; earlier lines are byte-identical
after the next cycle). Fields: `format`, `ops_id`, `started_at` / `finished_at` (UTC, from the host's
real clock), `duration_s`, `live_requested`, `status`, `exit_code`, `steps[]` (`name`, `command` as the
equivalent `assurance …` command line, `status`, `exit_code`, `duration_s`, `detail`, a few counts in
`info`), `human_actions[]` (`step`, `ref`, `action`), `not_established`.

It never holds key material, a passphrase, an API key, ledger contents or a step's raw output. Two
independent guards: raw output is never stored; and every string is filtered for the values of the
configured secret environment variables, the lines of the configured key file, PEM markers and long
base64-like runs. The key path is shown as `<configured key file>`. Treat the filter as defence in
depth, not as permission to put secrets in places they do not belong.

`human_actions` are derived from findings (a new or updated advisory finding, a stop-use match, a
changed or uncollectable machine, a filing prompt with no awareness decision, an anchor-all anomaly,
a backup that does not verify). They are prompts to read and decide. The record cannot tell whether a
person did.

### `ops status`

Reads the record (not the data). Prints the last cycle, its age, and the actions it raised, plus
actions raised by earlier cycles (last 30) and not raised again, labelled as such. Exit: `0` last
cycle ok and younger than `max_cycle_age_hours`; `1` last cycle flagged; `2` older than
`max_cycle_age_hours` (**stale**), no record at all, or last cycle degraded. Run it from a
monitor that is not the machine being monitored: a dead scheduler writes no record, so only a
reader elsewhere notices.

### Scheduling (examples; nothing is installed)

`deploy/assurance/ops/` has `cron.example`, `assurance-ops.service.example` +
`assurance-ops.timer.example` and `docker-compose.ops.yml`, each marked EXAMPLE, none with a secret
value (environment variable *names* only). Copying, reviewing and enabling them is the operator's
act. The cycle takes an exclusive `flock` on `<record>.lock`; a second cycle exits 2 with
`cycle already running` and writes nothing.

### Telling a person

Without this, the cycle record is read only if someone runs `ops status`. An optional `notify`
list in `ops.json` makes the **hosted/operator** cycle POST one small signed JSON message to an
HTTPS endpoint you name when a cycle is `flagged` or `degraded`. It is **off** unless configured.
The offline kit never loads it and opens no socket; `ops cycle --dry-run` sends nothing.

```json
"notify": [{
  "name": "oncall",
  "url": "https://hooks.example.invalid/neuralbridge",
  "allow_host": "hooks.example.invalid",
  "on": ["flagged", "degraded"],
  "secret_env": "NB_NOTIFY_HMAC_SECRET",
  "headers_env": "NB_NOTIFY_HEADERS"
}]
```

* `url` must be `https` (no credentials, port 443). `allow_host` is **required** and must equal
  the URL's host exactly (no wildcard, no sub-domain); the sender refuses any other host and
  follows **no** redirect on a POST.
* `secret_env` is the **name** of an environment variable holding the HMAC key; `headers_env`
  (optional) names one holding extra header lines, one `Name: value` per line, e.g.
  `Authorization: Bearer ...`. The values are read at send time and never written to the record,
  the outbox, stdout/stderr or an error message. A name that looks like a pasted key is refused.
  The URL path of a chat webhook can itself be a bearer token: it is never printed or recorded,
  so keep `ops.json` mode 0600.
* `on` defaults to both statuses. A quiet (`ok`) cycle sends nothing.
* `format` is `"json"` (default), `"slack"`, `"teams"` or `"pagerduty"`; see **Formats** below.
  `"servicenow_json"` is **not built** and is refused at config.

**Payload** (an allow-list built from the record; step `detail`/`info`/`command`, key and backup
paths, and ledger contents are never copied; finding text is neutralised, path-masked and
truncated):

```json
{
  "schema": "neuralbridge-ops-notify/1",
  "kind": "cycle",
  "cycle_id": "example-ops-20261102T031500Z",
  "ops_id": "example-ops",
  "started_at": "2026-11-02T03:15:00Z",
  "finished_at": "2026-11-02T03:17:41Z",
  "status": "flagged",
  "steps": [{"name": "watch.run:watch.json", "status": "flagged"},
            {"name": "ledger.verify", "status": "ok"}],
  "human_actions": [{"step": "watch.run:watch.json", "ref": "ADV-2026-001",
                     "action": "read new finding ADV-2026-001 (watch w1); ... Nothing was opened"}],
  "human_actions_omitted": 0,
  "record_sha256": "<64 hex>",
  "not_established": "A webhook delivery is not acknowledgement by a person. ..."
}
```

`record_sha256` is the SHA-256 of the cycle record as canonical JSON (sorted keys, compact
separators) **without** its `notifications` field, which cannot cover its own outcome. The body is
sent as canonical JSON, so the bytes you verify are the bytes that were signed.

**Headers**: `X-NeuralBridge-Signature: sha256=<hex>` (HMAC-SHA256 of the exact body bytes with
the secret), `X-NeuralBridge-Delivery: <uuid>` (new per attempt), `Idempotency-Key:
<cycle_id>:<target name>` (the same for every retry of that message), plus your `headers_env`
lines.

**Verify in a receiver** (compare in constant time; reject on mismatch; use the raw bytes, not
re-serialised JSON):

```python
import hashlib, hmac

def valid(secret: bytes, raw_body: bytes, header: str) -> bool:
    expected = "sha256=" + hmac.new(secret, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)
```

```sh
# body.json holds the raw request body; SIG is the X-NeuralBridge-Signature value
expected="sha256=$(openssl dgst -sha256 -hmac "$SECRET" < body.json | sed 's/^.* //')"
[ "$expected" = "$SIG" ] && echo valid || echo INVALID
```

(`-hmac "$SECRET"` puts the secret on a command line, visible to other local users; use it only
for an ad-hoc check, not in a long-lived script.) Deduplicate on `Idempotency-Key`.

**Delivery semantics.** A 2xx is `delivered`. 429 and 5xx are retried inside one attempt with
backoff, honouring `Retry-After` up to 30 s (a longer wait is not waited out). A failure is
appended to `<record>.outbox.jsonl` (append-only, mode 0600; it holds the message body, which is
the minimal payload above) and **retried at the next cycle with the same body and the same
`Idempotency-Key`**; after 5 attempts it is marked `abandoned` and shown by `ops status`. This is
at-least-once: a receiver can see a message twice. A target whose `secret_env` (or `headers_env`)
is not set is `skipped: secret_env not set`; the other targets are still sent. The cycle record
gains a `notifications` list (per target: `delivered`/`failed`/`skipped`, HTTP status, attempts,
delivery id, error *class* only, and whether it was a retry of an earlier cycle). **A failed
notification never changes the cycle's exit code or hides its result**, and `ops status` lists
recent failures, owed retries and abandoned messages. A retry of a message from an earlier cycle is
sent whatever the current cycle's status.

**Check and test.** `ops check` validates the `notify` block (https, host equality, whether each
environment variable is set in *this* shell, a warning for a token-like URL) and lists what it does
not check. `python -m assurance ops notify-test --config ops.json --target oncall` prints what a
test would send (the signature masked as `<hmac of N bytes>`); only with `--live` does it POST a
clearly labelled `status: "test"` message that contains no record contents. Exit `0` delivered,
`1` failed, `2` could not run.

#### Formats

`format` only changes the *shape* of the body. Every format is built from the same allow-listed
message above, so no extra data enters any vendor body, and the same neutralisation, path masking
and truncation already applied to finding text hold. **ServiceNow: `servicenow_json` is not built.**
For ServiceNow or Jira use `json` against an endpoint that takes arbitrary JSON, or a relay you
operate. The operator names the host in `allow_host`; no vendor host is trusted by name.

| `format` | body | what `secret_env` is | signature header |
|---|---|---|---|
| `json` | the generic body above | HMAC key | `X-NeuralBridge-Signature` |
| `slack` | `{"text": ...}` | HMAC key | sent, but Slack does not check it |
| `teams` | `{"text": ...}` | HMAC key | sent, but Teams does not check it |
| `pagerduty` | Events API v2 enqueue body | **the PagerDuty routing key** | **none** |

> **Auth asymmetry, read this.** For `json`, `slack` and `teams`, `secret_env` is an HMAC key and the
> request is signed. Slack and Teams do **not** verify that signature: for them the webhook URL
> *is* the credential (keep `ops.json` mode 0600; the path is never printed or recorded). The
> signature only helps if you put a relay of your own in front. For `pagerduty`, `secret_env` names
> the variable holding the **routing key** (PagerDuty's integration key), the key is sent only
> inside the body PagerDuty requires, and **no HMAC header is sent**. The routing key is read at
> send time and is never written to the record, the outbox, `ops status` or any log: the outbox
> stores the routing-key-free canonical message and the PagerDuty body is rebuilt on each retry.

Slack, `{"text": ...}` (`•` bullets, one per human action, Slack's `&amp; &lt; &gt;` escaping):

```json
{"text": "NeuralBridge ops example-ops: cycle flagged\nSteps: 2 total; not ok: watch.run:watch.json=flagged\nHuman actions: 1\n• watch.run:watch.json / ADV-2026-001: read new finding ADV-2026-001 ... Nothing was opened\nDrafted by software from an unsigned operator log; it decides nothing."}
```

Teams, `{"text": ...}` (plain text with `-` bullets; markdown punctuation is backslash-escaped):

```json
{"text": "NeuralBridge ops example-ops: cycle flagged\nSteps: 2 total; not ok: watch.run:watch.json=flagged\nHuman actions: 1\n- watch.run:watch.json / ADV-2026-001: read new finding ADV-2026-001 ... Nothing was opened\nDrafted by software from an unsigned operator log; it decides nothing."}
```

PagerDuty Events API v2:

```json
{"routing_key": "<from $secret_env>", "event_action": "trigger",
 "dedup_key": "example-ops-20261102T031500Z:oncall",
 "payload": {"summary": "NeuralBridge ops example-ops: cycle flagged; 1 human action(s): ...",
             "source": "example-ops", "severity": "warning",
             "custom_details": {"kind": "cycle", "cycle_id": "...", "status": "flagged",
                                "steps": [], "human_actions": [], "human_actions_omitted": 0,
                                "record_sha256": "<64 hex>", "not_established": "..."}}}
```

`severity` is `warning` for a `flagged` cycle and `error` for `degraded` (`info` for the
`notify-test` event). `dedup_key` equals the `Idempotency-Key` (`<cycle_id>:<target name>`), so a
retry updates the same alert instead of opening a second one. A `notify-test --live` to PagerDuty
**does trigger a real event** (`info`, summary "TEST message"); resolve it afterwards.

**Making text inert.** In step names, refs and action text: `@` becomes `@ ` (so `@channel`,
`@here` and `<@U123>` notify nobody); `://` becomes `:/ /` and `www.` becomes `www .` (no
auto-link). Slack: `&`, `<`, `>` are entity-escaped (this also defuses `<!channel>` and
`<url|text>`) and `*`, `_`, `~` and the backtick are replaced by look-alike characters, because
mrkdwn has no escape for them. Teams: backslash, backtick, `* _ [ ] ( ) < > & | ~ #` are
backslash-escaped. Newlines in finding text were already turned into visible `\n`, so a finding
cannot add bullets.

**Size caps.** Slack and Teams text: 3000 characters (our cap). PagerDuty `summary`: 1024
(Events API v2 limit). Over the cap, whole trailing bullets are dropped and the text says
`… (N more)` (N counts human actions not shown, including any the payload already omitted); an
over-long PagerDuty summary is cut and ends `… (N more)` (N counts characters). Nothing is cut
silently.

**Pointing a vendor at it.**

* *Slack:* create an Incoming Webhook in your workspace; `url` is the `https://hooks.slack.com/...`
  URL, `allow_host` is `hooks.slack.com`, `format` is `slack`. `secret_env` still needs a value
  (any HMAC key; Slack ignores the header).
* *Teams:* create a webhook / Workflows "post to channel when a webhook request is received" URL;
  `allow_host` is that URL's exact host, `format` is `teams`. A Workflows flow may need its trigger
  schema set to accept `{"text": ...}`.
* *PagerDuty:* add an *Events API v2* integration to a service, copy its integration (routing)
  key into the environment variable named by `secret_env`; `url` is
  `https://events.pagerduty.com/v2/enqueue`, `allow_host` is `events.pagerduty.com`, `format` is
  `pagerduty`. Do not put the key in `ops.json`.

```json
"notify": [
  {"name": "oncall", "url": "https://events.pagerduty.com/v2/enqueue",
   "allow_host": "events.pagerduty.com", "format": "pagerduty",
   "on": ["degraded"], "secret_env": "NB_PAGERDUTY_ROUTING_KEY"},
  {"name": "team-chat", "url": "https://hooks.slack.com/services/T000/B000/XXXX",
   "allow_host": "hooks.slack.com", "format": "slack", "secret_env": "NB_NOTIFY_HMAC_SECRET"}
]
```

`ops check` and `ops notify-test` (dry run) print the format and the body shape; the dry run shows
the body with the routing key masked.

**Verified against vendor docs only, not against a live account.** The Slack, Teams and PagerDuty
bodies are built from each vendor's published request schema and checked by golden contract
fixtures in `tests/test_ops_notify_formats.py`. No Slack workspace, Teams tenant or PagerDuty
account was contacted, so whether a given endpoint accepts a body (a Teams Workflows trigger schema,
an org-specific Slack restriction, a PagerDuty rate limit) is unknown until you run
`ops notify-test --live` against it.

**Not established by this.** That the receiver exists, authenticates the signature, or keeps the
idempotency key (`ops check` makes no request); that a delivered (2xx) webhook was read by anyone,
let alone acted on: it is not acknowledgement by a person, and awareness, a case and its closure
remain a named person's decisions; that a webhook that was never retried or was abandoned is
anything but a gap in who was told; that the host's clock, DNS or egress firewall let it through.
Customer ledger contents are never sent: only the strings already in the cycle record's
`human_actions` (advisory ids, machine serials, step names) leave the host.

## 3. Upgrade

An upgrade changes code that reads and writes the ledgers. Take the safety net first and prove it.

1. **Before.** Run a cycle (or `restore_check backup`) and verify the result:
   ```bash
   python -m assurance ops cycle --config /etc/assurance/ops.json     # exit 0 or 1
   python -m assurance.evidence.restore_check verify /srv/assurance/backups/<newest>   # exit 0
   python -m assurance ops status --config /etc/assurance/ops.json
   ```
   Store the `manifest_sha256` from the backup step (in the record, `steps[].info`) somewhere other
   than this host. Stop here if anything is not 0.
2. **Stop the writers** (the api, the timer): one writer per ledger file. `systemctl stop
   assurance-ops.timer` / `docker compose stop ops-cycle api` as applicable.
3. **Upgrade** by repeating section 1 at the new commit in a **new** venv (or new image); keep the old
   one until step 6. Record the new commit, `pip freeze` and digest.
4. Run `python -m assurance capabilities --check` and `python -m assurance ops check --config …`
   with the new code.
5. **Start** the api, then run one cycle by hand.
6. **After.** Verify the *new* backup the cycle just took as in step 1. Then
   `restore_check verify --against-live /srv/assurance/data <the pre-upgrade backup>` (a
   copy of it in a scratch directory): it fails a backed-up ledger that shares a ledger id
   with a live one but disagrees with it (a fork). Only then remove the old venv or image.
7. **Rollback**: stop writers, restore the old venv or image, start. If the data were changed by the
   new code and you need the old state, that is a restore (section 4), and anything appended after
   the backup is lost; say so in your log.

## 4. Backup and RESTORE DRILL

`restore_check backup` snapshots `accounts.db`, the operator ledger and every tenant ledger
transactionally (a plain file copy of a WAL database can lose its newest records), copies the
attestation and supplier-feed logs, and writes `backup-manifest.json` (every file's size and SHA-256,
each ledger's length and head link hash, the accounts). The directory is `0700`, files `0600`, and
`pending_keys` (API keys minted by a checkout and not yet collected) are **not copied**: a customer
whose key was unclaimed at backup time needs a new one after a restore.

A backup is only a backup once a restore has been shown to work. Do the drill **before** you rely on
the cycle, after every upgrade, and on a schedule you set. Never on the production volume:

```bash
SCRATCH=$(mktemp -d /var/tmp/restore-drill.XXXXXX)        # not under the data directory
BK=/srv/assurance/backups/<timestamp>                      # a backup directory the cycle made
# 1. restore = copy the backup tree to a scratch directory, preserving modes
cp -a "$BK"/. "$SCRATCH"/
# 2. the restored copy verifies from its own files and manifest
python -m assurance.evidence.restore_check verify "$SCRATCH"             # expect exit 0
# 3. and agrees with the live volume's history (fails a fork or a rewound ledger)
python -m assurance.evidence.restore_check verify --against-live /srv/assurance/data "$SCRATCH"
# 4. the operator ledger and every tenant ledger verify as the product reads them
python -m assurance art14 --ledger "$SCRATCH/art14-register.db" verify
for L in "$SCRATCH"/tenants/acc_*.db; do python -m assurance art14 --ledger "$L" verify || echo "FAIL $L"; done
# 5. completeness against the signed anchor (needs the PUBLIC key from outside the backup)
python -m assurance art14 --ledger "$SCRATCH/tenants/acc_<id>.db" verify \
    --attestations "$SCRATCH/attestations/acc_<id>.jsonl" --public-key /path/to/anchor.pub
rm -rf "$SCRATCH"                                          # when done; it holds customer evidence
```

Pass criteria: step 2 exit `0`, step 3 exit `0`, every `art14 verify` exit `0`; step 5 exit `0` for an
account that has an anchor. Exit `3` from `restore_check verify` means *unchecked* (no manifest), and
is not a pass. Record in your own decision log: date, backup name, the `manifest_sha256` you stored at
backup time and the one `backup` prints now, results, who ran it.

What the drill does **not** show: that the manifest was not rewritten together with the data (the
manifest is checksums, not a signature; keep `manifest_sha256` elsewhere), that an attestation log's
records are genuine without the public key, or that the backup exists off this host. An
off-host copy is the operator's to make; nothing here does it.

The cycle takes a new timestamped backup directory each time and deletes none. Retention (and the
disk it uses) is not managed; `ops check` measures free space once.

## 5. Health

- **Is it running?** `ops status` exit 0. Stale (exit 2) means no cycle finished within
  `max_cycle_age_hours`: the timer stopped, the host was down, or cycles are failing before they write.
- **Is it sound?** Read the last cycle's `steps[]`. `ledger.verify` and `backup.verify` must be `ok`.
- **Can it still be restored?** The last drill's date and result (section 4). `ops` does not run the drill.
- **Key and anchors.** `python -m assurance attest preflight --key … --anchors … --max-age …`
  (`ATTEST.md`) reads the anchors that exist.
- The compose healthcheck is `ops status`; it turns unhealthy when the last cycle is degraded or stale.

## 6. Incident handling

First, preserve: stop writers, copy the data directory (a backup into a *new* directory is safe), and
write down the time and what you saw. Do not delete or "repair" a ledger in place.

**Chain verify fails** (`ledger.verify` failed; the cycle degrades; anchors are skipped; the backup is
kept and flagged). 1) `python -m assurance art14 --ledger <path> verify` prints the sequence numbers of
the breaks. 2) Compare with the newest backup that verified (`restore_check verify --against-live`) and
the last attestation. 3) Treat the live ledger as untrusted until a person has decided what happened;
the damaged file is evidence, keep it. 4) Restore from the newest verifying backup into a scratch
directory first (section 4) and compare. 5) Anything appended after that backup is not in it. A hash
chain detects accident, not a determined insider who can rewrite the ledger and its log together.

**An anchor is contradicted** (`attest anchor-all` flagged a ledger, or `art14 verify --attestations`
says the ledger is shorter than, or does not contain, a signed head). That is evidence that records were
removed or rewritten after the anchor, or that the log and ledger are from different lineages. Do not
re-anchor over it (anchoring would sign the contradicted state). Stop writers, preserve both files,
verify the log with the public key obtained elsewhere (`attest verify`), then proceed as for a failed
chain. Anchors you wrote before the break remain valid statements about what they covered.

**Intel is stale** (`watch run` DEGRADED with `stale`; or steps show `not refreshed` for days). The
refresh did not run: `live` false, `--live` not passed, the host unreachable, or the source rejected the
request. Read the `intel.refresh:*` rows and `intel history`. Until a refresh succeeds, a quiet watch
does not mean the fleet is unaffected. Do not widen `max_age_hours` to silence it.

**The key is suspected compromised.** Follow `KEY-CEREMONY.md`, sections 6 (rotate) and 7 (revoke),
and the decision record in section 9. Remove the key from the cycle config (`attest` omitted: the
cycle then skips anchoring and says so) rather than leaving a suspect key signing. Existing anchors
made by that key can no longer be trusted as independent of whoever held it; say so. A rotation
creates a new key; it does not repair history.

**Backup does not verify.** The step is `failed` and the cycle degrades. Do not delete older backups.
Re-run `restore_check verify` by hand on it, read the problems, and take another backup. If the live
data are healthy and a fresh backup also fails to verify, stop and investigate before the next upgrade.

**Cycle already running / lock stuck.** `flock` is released by the kernel when the process ends, so a
stale lock file with no holder does not block. A cycle that never ends is a hung step; inspect the
process rather than deleting the lock.

## 7. Not established

This tooling and this runbook do **not** establish:

- That a scheduler is installed, enabled or running (only a stale `ops status` shows it stopped).
- That the key is held safely, was never copied, or that a recoverable copy exists (`KEY-CEREMONY.md`
  is the procedure; `ops check` checks a file's mode and that it sits outside the data directory).
- That an off-host backup exists, or that any backup restores, until a drill has been performed and
  recorded. `ops cycle` verifies the backup it just took against its own manifest.
- That the cycle record is genuine or complete: it is an unsigned, unchained operator log.
- That a quiet watch means the fleet is unaffected; that a public record, KEV entry or EPSS score is
  correct, complete or current; that a vendor advisory applies to a site's installed firmware.
- That a machine is safe, that a case is closed or that anyone decided anything: `ok` means a step's
  own exit code was 0.
- That the clock of the host is right.
- That a notification target exists, authenticates or is read by anyone; webhook delivery is not
  acknowledgement by a person ("Telling a person").
- That the Python dependencies at install time match any earlier install (no lock exists).
- Anything about legal or regulatory status. No step here says a machine, a filing or an organisation
  complies with anything.
- Postgres, the `/ai` control plane and the website are outside this runbook.

## 8. What we measured

One run of `scripts/bench_scale.py` on one machine, before and after three fixes (below). These are
measurements of this code on this host, not a capacity statement.

**Machine.** 2026-11-02; 4 vCPU Intel Xeon @ 2.10 GHz, 16 GB RAM, Python 3.13.18, Linux 6.18 in a
VM; disk type not probed. The host was shared with other jobs: the 1-minute load average was
3 to 12 during the baseline and 5 to 9 during the "after" run, so absolute seconds are noisy (the
same append loop ran at 3.5 and 6.3 ms per append in two runs of unchanged code). Read the shape
(the exponent) before the seconds. Data is synthetic: each machine is one manifest plus one
enrolment record (2 ledger entries, about 4.4 KB each on disk), two items, one declared safety
function, no verifications and no open cases.

**Fleet size N (machines), seconds, before -> after.** "Before" is commit `c505cc6` unmodified.

|---|---|---|---|---|
| `machinery import-inventory` (CLI) | 3.3 -> 1.4 | 44.9 -> 9.1 | 577.7 -> 26.5 | 1.72 -> 0.98 |
| `POST /v1/machinery/enrol/batch`, 200 rows per request | 2.6 -> 1.4 | 36.4 -> 8.0 | 493.5 -> 35.2 | 1.74 -> 1.08 |
| `fleet list` (CLI) | 0.43 -> 0.28 | 4.0 -> 1.6 | 22.4 -> 5.3 | 1.32 -> 0.99 |
| `GET /v1/fleet/machines` | 0.58 -> 0.39 | 3.2 -> 1.5 | 18.2 -> 5.2 | 1.15 -> 0.86 |
| `report build` (CLI) | 0.49 -> 0.31 | 2.9 -> 1.6 | 18.4 -> 5.7 | 1.21 -> 0.98 |
| `GET /v1/fleet/report` | 0.85 -> 0.32 | 3.7 -> 1.3 | 20.7 -> 5.1 | 1.06 -> 0.92 |
| `machinery coverage` (one machine) | 0.02 | 0.12 | 0.43 | 1.01 -> 0.96 |

The slope is the log-log fit of time against N over the three sizes (1.0 is linear, 2.0 is
quadratic). It includes process start-up and per-call fixed cost, so it understates growth at
small N. Peak resident memory of the largest read cases was 129 MB at N=2000 (17.5 MB database).

**Ledger size (entries), seconds.** Linear in every case (slopes 0.9 to 1.05); unchanged by the fixes.

| operation | 1,000 | 10,000 | 50,000 |
|---|---|---|---|
| append, one writer, whole loop | 3.5 to 6.3 | 50 to 80 | 184 to 231 |
| `verify_chain` | 0.06 | 0.65 | 2.3 |
| `export` | 0.08 | 0.78 | 3.2 |
| `verify_report` | 0.08 | 0.65 | 2.5 |
| enrol one machine (it verifies the chain first) | 0.06 | 0.54 | 2.4 |

Tenant export of a 10,000-entry ledger: 2.2 s, 22 MB written, 117 MB peak. The whole
50,000-entry case (build, verify, export, read everything) peaked at 408 MB; the export bundle is
built in memory. Intel store with 3,000 observations
(750 repeats of the four repo fixtures): ingest 21 s in total, `intel history` 0.28 s,
`intel candidates` 0.01 s; the repeats are the same bodies, so the candidate set did not grow and
that figure does not show how candidates scale with distinct advisories.

**Write throughput is bounded by one SQLite file with one writer.** Every append is its own
transaction with `synchronous=FULL` (an fsync), and a tenant ledger has exactly one writer. On
this host that was **125 to 290 appends per second** (3.5 to 8 ms each; it varied with host load,
not with ledger size). A machine enrolment is two appends, so one tenant's enrolment ceiling here
is about 60 to 145 machines per second before any other work; the measured 2,000-machine import
(4,001 entries) took 26.5 s, about 150 entries per second. Two tenants write to two files and do
not share this bound; one tenant's concurrent writers queue on its file. Raising it would mean
weakening the commit guarantee or batching commits, and neither was done.

**What changed.** 1) The batch importer verified the whole chain before every row (O(rows x
entries)); it now walks the chain in full once before the first row, checks the head it holds
plus everything appended since before each row, and walks in full again after the batch record
(`BatchChain` in `machinery/enrol.py`). A broken chain is still refused up front with nothing
written; an old record edited mid-batch is found by the closing walk, not by each row, and the
import then fails with `ledger_chain_unverified` (409 on the API) although earlier rows were
written. `enrol_machine` without a `BatchChain`
(`machinery enrol`, `POST /v1/machinery/enrol`) still walks the whole chain per call.
2) `subject = ? AND kind = ?` queries were answered from the kind index and scanned every row of
that kind (one scan per machine: fleet reads, enrolment, the compare-and-swap in `append`); they
now use the subject index (`+kind`, no schema change, no migration, same rows in the same order).
3) Nothing else was changed: the 60 s `ASSURANCE_CHAIN_RECHECK_SECONDS` window and the full
verification before `READY_TO_CLOSE` are as before, and no hash or serialisation format moved.

**Still linear by design.** Any read that must vouch for the chain walks it (about 55 microseconds
per entry, so 0.2 s for a 2,000-machine fleet), and a fleet read costs about 2.5 ms per machine in
separate ledger reads. These grow in proportion to the fleet, not faster.

**What this does NOT establish.**

- Not a capacity or latency guarantee, and not a statement about any other hardware, disk, Python
  or load. One host, one run per size, a shared and noisy machine, disk type unknown.
- Synthetic data only: machines with two items and no verifications, no open change cases, no
  amendments, one site-per-20 pattern. A real fleet with many verifications per machine, large
  manifests or many cases will cost more per machine; none was measured.
- No concurrency test: one reader or writer at a time. Two writers on one ledger, many tenants at
  once, lock contention and the hosted process model were not measured.
- No network: the API cases use an in-process ASGI client. Latency over a network, TLS, a proxy or
  the hosted volume was not measured.
- Nothing about sizes above 2,000 machines or 50,000 entries, or about Postgres-backed parts.
- The "before" figures come from two runs on a busier host; the speed-ups quoted are the order of
  magnitude, not a precise ratio.

To repeat: `PYTHONPATH=src python scripts/bench_scale.py --out result.json` (about 20 minutes;
`--sizes`, `--ledger-sizes` and `--only` narrow it). `tests/test_scale_smoke.py` and
`tests/test_assurance_batch_chain.py` guard against a return to quadratic behaviour; they are not
performance claims.
